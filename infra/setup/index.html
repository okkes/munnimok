The wizard works through a small helper on this machine: it keeps the values you paste (a gitignored store), runs the local platform, writes the platform config and asks the providers, the NAS and Logto what a browser cannot. Start it, and it opens this page itself.

infra\setup\start.cmd        (double-click it — or: node infra/setup/serve.mjs)

1 Platforms

Every platform runs the same design: one shared stack (munni-<platform>-shared — GlitchTip, the vault, pgAdmin, the control cockpit) and any number of environments (munni-<platform>-<env> — web, admin, api, its own Logto and its own Postgres). Pick the platform this page works on; the steps below follow it.

2 Features & accounts

Tick what you want — everything else works out of the box (offline-first app, web push, sync). Each tile is one feature with its account: the chip says what it still needs, Manage opens what the service is, why munni needs it, where the values come from and the fields. Save keeps a value in the helper's store for this platform only — platforms share nothing: each has its own values, ticks and GitHub connection — and, for the NAS, copies it into this platform's GitHub environments (values are write-only there). The ticks are the defaults of every environment you add; an environment's own features can differ. Skip for now counts an integration as done until you come back to it.

    Connection

    One fine-grained token per platform drives this page live and is stored as the repository secret GH_PAT so the workflows can manage environments and write secrets back. Point it at a repo that carries munni — or at a name that does not exist yet, and this page copies okkes/munnimok under it. Branches are munni's own (dev/master), picked automatically. A working token is kept in the helper's store — the next visit reconnects by itself.

    How to create the token (2 minutes)
    1. Open github.com/settings/personal-access-tokens/new.
    2. Repository access: Only select repositories → your munni repo. (If you want this page to CREATE the repo as a copy, pick All repositories instead — a fine-grained token cannot pre-select a repo that does not exist yet.)
    3. Repository permissions: Administration Read and write · Secrets Read and write · Variables Read and write · Actions Read and write · Contents Read and write · Workflows Read and write (the last two let this page keep a copy's pipeline files in step with upstream).
    4. Generate, copy the github_pat_… value and paste it below. Set a long expiry — rotating it means redoing only this step.

    What's left for this platform

    Everything this page can do, it does by itself. This list is what stays yours at the PLATFORM level — in order, detected wherever a provider lets us check. Each environment lists its own steps in its workspace below. “open” jumps to the exact spot.

      Set up & start everything one button

      One button does the whole platform: mints the secrets, starts the shared services (munni-lcl-shared), creates the prod environment when none exists yet, and brings every environment up — waiting for each piece and wiring sign-in, crash tracking, the vault and (when a feature needs the network) the https mode with its certificate automatically. When Windows asks to trust a root certificate mid-setup, that is the platform's own — approve it. Pressing it again is always safe, it only fills gaps.

      Keeps itself up to date

      The setup above is a ONE-TIME bootstrap. From then on the helper is this PC's counterpart of the NAS deploy poller: every 10 minutes it fetches this checkout's branch, fast-forwards when the working tree is clean, re-renders every stack after a pull, pulls the newest image of each channel and brings the platform up again — restarting itself when its own code moved. Register it at logon and it runs without this page.

      Shared services

      The platform's common ground, always running — Set up starts it, Stop/Delete everything are the only ways it goes down. addresses appear once the platform is set up — the control cockpit signs in through the control environment (the platform's lowest slot unless you pick another); pgAdmin is one console over every database server (logins under Reveal secrets, servers preregistered).

      Your secrets & the vault read them back any time

      Every generated or saved secret lives readable in this machine's gitignored stores (the wizard's own, one per stack) — and a Vaultwarden vault runs in the shared stack at localhost:8384 as the human copy, usable with the real Bitwarden apps. One button does the whole vault: creates the account with a generated master password (shown under Reveal), imports every sign-in and secret as vault items (one folder per stack), and closes signups. Re-press it any time to re-sync. The vault is served over https with a locally-minted certificate — your browser warns ONCE about it; choose Advanced → proceed, it is your own machine signing for itself.

      Developer extras — not needed to run munni

      The from-source dev loop develop against it

      API + Logto + Postgres in docker built from THIS checkout, the app via npm run dev with hot reload (run that in a terminal; details in deploy/README.md). Separate from the environments above, which run released images.

      Platform accounts

      What the whole platform needs once: its domain, the DSM account the pipeline deploys with (Check asks DSM from this machine), and — optional — a registry token for private images and a Let's Encrypt contact. Saved values sit in the helper's store and, once GitHub is connected, in the platform's GitHub environments (nas-shared and every nas-<env>).

      Published path & control environment

      The File Station folder the deploy bundles land in (committed as publishedPath, stored as SYNOLOGY_PATH); the live dir with the poller is its parent. The control environment is the one whose API and Logto the control cockpit signs into — the lowest slot unless you pick another.

      Vault account

      The platform's Vaultwarden (vault-nas.<domain>) keeps every credential the bootstrap mints — Logto's console login, the machine credentials, each Postgres, the GlitchTip admin — one folder per stack. The helper generates the account (e-mail + master password) into its store; Set up shared services copies it into the GitHub environments so the bootstrap can sign in. The master password is under Reveal.

      Set up shared services one button

      Creates the GitHub environment nas-shared, stores every platform value into it (and into every existing nas-<env>), commits the platform config to the branch and dispatches Bootstrap for munni-nas-shared: it mints the generated secrets, writes the reverse-proxy rules, requests the wildcard certificate through DSM, ensures the live dir and the poller task, renders the stack — and chains Deploy, which uploads the bundle the poller applies within five minutes. Re-pressing is safe; it only fills gaps. The NAS status below tells what is left.

        4 Environments

        Each environment is a full munni of its own — isolated sign-in, database and addresses, its own store identity for the phones. Its workspace holds everything that carries ITS name: what it runs, the registrations at the providers, its phones, who may administer it, and how it goes away.

        5 Leftovers — by hand

        Everything else on this page is code. These have no API — they stay yours, each once.

        • 1
          Store records of removed environments
          Play Console and App Store Connect cannot delete an app record by API. After a Clean up, retire them there: Play Console → the app → Advanced settings → unpublish/delete; App Store Connect → the app → Remove app (once every build is expired — the Phones tab's Retire does that part).
        • 2
          The DSM deploy account (Synology NAS)
          Control Panel → User & Group → the deploy user → Edit → Applications: DSM = Allow, File Station = Allow (a group's Deny beats Allow) → User groups: administrators → Save. 2-step verification off for it, and Adaptive MFA off for administrators (Security → Account) — no account can grant itself any of this. Check on the Synology tile tells whether DSM accepts it.
        • 3
          DNS for an own domain
          Synology DDNS resolves *.<domain> by itself — nothing to do. An own domain needs a wildcard record pointing at the NAS (the hosts are munni-<env>-nas, -api, -admin, -logto, -logto-admin, and glitchtip-nas, vault-nas, control-nas, pgadmin-nas); the wildcard certificate then comes from acme.sh with the synology_dsm hook.
        • 4
          The APNs key upload for iOS push
          Once per Apple team: developer.apple.com → Keys → a key with Apple Push Notifications service → download the .p8. Then Firebase console → the Play service account's project → Project settings → Cloud Messaging → the iOS app → APNs Authentication Key → Upload (key, Key ID, Team ID). Google offers no API for this step.
        • 5
          Trusted local CA roots on this computer
          Every https family (LAN mode) mints its own "Caddy Local Authority" root and Trust CA puts it in your Windows user store. No wipe can take it out again — Windows untrusts a root only through its own consent dialog, one per entry. After a Clean up: certmgr.msc → Trusted Root Certification Authorities → Certificates → delete every "Caddy Local Authority" row. The Clean up log counts the stale ones for you.
